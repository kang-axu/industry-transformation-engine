# ITE Specification v0.1

## 1. Purpose

ITE defines a repeatable operating system for transforming a real industry around a new general-purpose technology while retaining reusable organizational capability from each transformation.

The engine must improve after every real project.

If each new industry requires the organization to relearn the same generic lessons from zero, ITE has failed.

---

## 2. Transformation Lifecycle

### T0 — Find Giants
Identify proven operators, workflows, companies, artifacts, standards, and historical precedents before designing from first principles.

### T1 — Business Decomposition
Map the real business:
- value creation
- acquisition
- judgment
- execution
- handoffs
- constraints
- failure modes
- responsibility boundaries

### T2 — Human Calibration
Collect real language, expert judgments, positive/negative cases, exceptions, rejection reasons, and acceptance criteria.

No bulk automation before calibration.

### T3 — Data Acquisition
Gather the minimum real data needed to model and validate the workflow.

Prefer reality over synthetic assumptions.

### T4 — Workflow Redesign
Do not merely add AI to the existing process.

Ask which steps can disappear, merge, move earlier, move later, or become continuous feedback loops.

### T5 — AI Insertion
Assign AI only where it has a clear role:
- perception
- retrieval
- classification
- ranking
- drafting
- decision support
- orchestration
- anomaly detection

### T6 — Human-AI Role Design
Define:
- what AI may do autonomously
- what requires approval
- what must escalate
- who owns the final responsibility

### T7 — Real-World Validation
Test against real outcomes, not internal confidence.

### T8 — Experience Capture
Record:
- success patterns
- failure patterns
- human corrections
- edge cases
- operational costs
- outcome evidence

Failures that matter should enter FTD.

### T9 — Standard Upgrade
Convert validated learning into:
- rules
- schemas
- modules
- checklists
- evaluation sets
- escalation policies
- reusable code or tooling

Then begin the next cycle.

---

## 3. Reuse Test

A transformation creates organizational capability only if some part of the result can reduce the cost, time, or error rate of future transformations.

Every completed project should answer:

1. What did we learn that survives this client?
2. What did we learn that survives this industry?
3. What did we learn that survives the current model/tool stack?
4. What should become standard?
5. What should remain local?
6. What should never be automated?

---

## 4. Standardization Boundary

ITE separates three layers:

### Core Layer
Cross-industry capabilities that should be reusable:
- ingestion
- deduplication
- storage
- parsing
- candidate detection
- ranking
- human review
- feedback
- outcome tracking
- evaluation
- versioning
- auditability

### Industry Layer
Industry-specific:
- terminology
- thresholds
- workflows
- risk rules
- domain entities
- compliance boundaries
- expert heuristics
- outcome definitions

### Client Layer
Client-specific:
- channels
- permissions
- staff
- pricing
- data sources
- local rules
- commercial constraints

The design goal is not maximum standardization.

It is correct separation.

---

## 5. Learning Layer

ITE is paired with Failure Training Data (FTD).

ITE transforms industries.

FTD turns meaningful failures into reusable behavioral change.

FTD lifecycle:

`FAILURE → HUMAN CORRECTION → VALIDATION → BEHAVIORAL UPDATE`

ITE should consume validated FTD rules where relevant.

---

## 6. Economic Rule

Each transformation should aim to move from:

`CUSTOM WORK → REUSABLE METHOD → REUSABLE MODULE → REUSABLE SYSTEM`

The organization should become faster and cheaper at solving recurring classes of problems.

Revenue without reuse is service income.

Revenue plus reusable capability is compounding.

---

## 7. Risk Rule

Do not confuse outcome alignment with uncontrolled risk transfer.

Prefer:
- implementation fees
- recurring system fees
- usage or verified-output fees
- upside sharing where measurable

Be cautious with:
- unconditional guarantees
- fixed-price commitments under uncontrolled scope
- absorbing client operating risk
- taking responsibility for variables outside system control

---

## 8. Evidence Rule

No rule becomes durable merely because:
- an expert said it
- an AI inferred it
- a document stated it

Reality has final authority.

Validated experience should survive:
- model changes
- tool changes
- agent changes
- workflow changes

---

## 9. Status

ITE v0.1 is experimental.

The specification is expected to change through real deployment, failure, correction, and validation.
